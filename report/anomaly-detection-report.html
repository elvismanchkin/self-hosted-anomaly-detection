Anomaly detection on the stack you already run

For 200 GB–2 TB of logs a day and 1–10 M active series: shrink every signal to a few thousand aggregates, run cheap statistics on all of them, page only on SLO burn, and let an LLM see alert bundles — never raw data.

Findings

What the research found

Logs

Elastic's own log anomaly detection is not free

ML jobs, log categorization, the AIOps tools, and ES|QL CATEGORIZE / CHANGE_POINT all need Platinum+. Kibana Basic can alert only to Index and Server log (the Cases connector is Platinum), so it can't send a webhook. The free route is ElastAlert2 on top of a stateless template key, rolled up per minute by a transform, which is free on Basic.

Metrics

The best free detector is plain PromQL

grafana/promql-anomaly-detection provides adaptive (mean ± 2σ) and robust (median ± 2·MAD) seasonal bands as recording rules, with no plugin and no feature flag. Run it on tagged service-level series only. Grafana OSS has no ML: Grafana ML and Sift are Cloud-only.

Traces

Traces are best handled as metrics

An OTel Collector tier in front of Jaeger turns 100% of spans into RED metrics, then keeps errors, slow traces and 2% of the rest. The metrics feed the same bands and SLO rules as everything else. Jaeger v1 has been end-of-life since 2025-12-31.

Methods

Simple beats clever at this scale

On TSB-AD, simple statistical methods (Sub-PCA 0.42, POLY 0.39 VUS-PR) beat forecasting foundation models (TimesFM 0.30, Chronos 0.27). Template novelty and count methods are competitive with deep learning on the public log datasets. None of the operators cited pages on raw anomalies; Uber and Netflix page on anomaly output only after a confirmation stage or health model.

LLM

An LLM only fits at the tail

One call per Alertmanager group, with a ≤ 20k-token bundle of pre-summarised evidence and a hard monthly cap. HolmesGPT can run on demand for deeper investigations. Anything upstream of the detectors is 3–6 orders of magnitude too expensive.

Cost

Managed alternatives cost thousands a month

At list prices, this volume costs ≈ $8.1k–$85k/month on Grafana Cloud Pro (60 s scrape), ≈ $62k–$609k/month on Datadog, and ≈ $2.3k–$17k/month on Elastic Serverless Complete, whose "as low as" rate applies only above 150,000 GB/month. Self-managed Elastic Platinum is quote-only and sold to existing customers only.

Design

Four tiers, one pager

Each tier runs on less data than the one before and costs more per item. Findings from tiers 1–3 go to chat, grouped per service, and are muted while a page for that service is firing.

  1. T0

    Rules and SLO burn rate

    Multi-window, multi-burn-rate alerts (14.4× over 1 h/5 m, 6× over 6 h/30 m), generated with Sloth or Pyrra. Heartbeats, flatlines and predict_linear for capacity.

    poc/prometheus/anomaly-alerts.yml
    Pages on-call
  2. T1

    Cheap statistics on every aggregate

    Adaptive and robust PromQL bands on 3–5k service-level series. ElastAlert2 new-template and template-spike rules on the 1-minute log rollup; flatline and error-ratio rules on the raw indices. Log-novelty alert on template counts.

    poc/prometheus/anomaly-inputs.yml · poc/logs/elastalert2/ · poc/logs/elastic/
    Chat / ticket
  3. T2

    ML on the top-K series

    A seasonal-median + MAD scorer (Python, or the Go port in anomalyd) exports anomaly_score, and can be upgraded to statsforecast MSTL or Matrix Profile. It confirms tier-1 candidates rather than paging anyone.

    poc/ml/prom_anomaly_job.py
    Second opinion
  4. T3

    LLM on alert bundles

    A bundle per Alertmanager group: related series, template deltas with redacted samples, and error trace IDs. One cheap-model call with capped output. HolmesGPT runs on demand, ≤ 20 per day.

    webhook route in poc/prometheus/alertmanager.yml
    On demand, capped

Architecture

Where it plugs in

Nothing in the core path changes. The additions are Filebeat processors, one ES transform, ElastAlert2, a collector tier in front of Jaeger, recording rules, and a small scorer.

  • Why the key is added in Filebeat: Filebeat allows exactly one output, and re-reading 2 TB/day out of Elasticsearch would be a second workload as large as ingest. So the template key is added in Filebeat or an ingest pipeline, and the transform rolls it up.
  • Optional AD Prometheus: a small second Prometheus, fed by a remote_write keep-filter, can hold the ~100k recorded series for 90 days. Weekly bands need 7 days of history and SLO windows need 30, so this avoids raising retention on the big server.
  • Pilot alternative for logs: an OTel Collector file_log → container → drain → count DaemonSet reads the same container stdout files as Filebeat and sends template counts to Prometheus, so logs and metrics share one set of detectors.
  • Build option: anomalyd replaces the scorer's per-run query_range with remote_write and adds a per-host Drain agent that ships counts, not lines.

Plan

Roadmap

Iteration 1 only adds components. Swaps and heavier models come only after iterations 1–2 produce evidence on our own incidents.

Step 0 · half a day

Confirm what runs

  • GET /, GET _license, GET _xpack: expect basic, with ml ✗ and transform ✓
  • Prometheus buildinfo and status/tsdb for top cardinality
  • Jaeger version: v1 is end-of-life
  • Filebeat ≥ 7.8? Apps on OTLP or Jaeger SDKs?
Iteration 1 · weeks 1–4

Add-ons only

  • Alertmanager as the single bus; ElastAlert2 → API v2
  • SLO burn-rate alerts for the top 10–20 services
  • OTel tiers in front of Jaeger (span metrics, tail sampling)
  • Template key in Filebeat, then the 1-minute transform
  • Tag 3–5k inputs and load the upstream band rules
  • Exit when no anomaly pages anyone and every rule's precision is measured
Iteration 2 · months 2–3

Confirm and explain

  • Tier-2 scorer on the top-K series; MSTL if needed
  • Pilot OTel drain + count on a few hosts
  • LLM triage webhook with a $100/month cap and redaction
  • HolmesGPT on demand; Keep OSS if grouping isn't enough
  • Evaluate on the incident log, never with point-adjusted F1
Iteration 3 · quarter 2+

Only with evidence

  • Jaeger v2 upgrade, if still on v1
  • Kafka tee, if several consumers need the raw stream
  • Thanos (additive), or Mimir/VictoriaMetrics, for > 90 days of history
  • OpenSearch RCF, if log detection on the rollup falls short
  • Foundation models, if a back-test shows lift

Build option · iteration 2 pilot

anomalyd: the same detectors in one Go binary

A second, separate PoC in anomalyd/, one static binary with one third-party dependency. anomalyd agent reads the container stdout files Filebeat already ships (a DaemonSet next to Filebeat), mines Drain templates on the node and sends only per-template counts. anomalyd server takes the anomaly inputs through remote_write, backfills their history from Prometheus once, scores every series against the same seasonal median + MAD baseline as the Python scorer, spots new log templates, and sends tier-labelled findings to Alertmanager.

Log lines mined per second on one core, synthetic Filebeat-style logs

JSON parse, masking and Drain included; about 150 B per line and 23 templates, so every figure is an upper bound for real logs. "Container stdout" is the same file wrapped as containerd writes it (CRI envelope per line), which is what Filebeat reads here. Drain3 ran on the host on a 300k-line file; OTel and anomalyd ran on the same 3M-line files in Docker with --cpus 1 (OTel time includes start-up). Commands: anomalyd/test/bench/compare.sh, with CONTAINER=cri for the stdout rows.

Evidence

Validated locally

Every PoC piece ran on synthetic data, in Docker or local Python. Nothing touched our real systems. Not verified: real-log throughput, Filebeat regex CPU, tail-sampling memory at real span rates, ElastAlert2 on ES 7.x.
